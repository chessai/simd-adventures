# Blocked Bloom and cuckoo filters with SIMD backends — design, measurements, analysis

All numbers below were measured in this session on a 2-vCPU KVM guest (Intel Xeon, model 207 = Emerald Rapids,
nominal 2.1 GHz, L1d 48 KiB, L2 2 MiB per core, L3 reported as 260 MiB but see §4), GCC 13.3 `-O3`. The
AArch64/NEON backend was cross-compiled and validated under qemu-user; it has not been benchmarked on real
hardware. Hardware performance counters are **not** exposed in this guest (`perf_event_open` → `ENOENT`), so
the counter columns are empty here; the harness (`include/vf/perf.h`) is complete and the CSV has the columns.
Everything else — throughput, memory-bound behaviour, FPR, bits/key — is real.

Every number in the tables comes from `results/*.csv` and `results/*.txt`, regenerated by `scripts/run_all.sh`
and `scripts/make_report.py`.

## 1. Design

### 1.1 Hash: one function, scalar and 8-wide, bit-identical

`vf::hash1(key) → (hb, hl)` and `vf::hash8<Ops>(...)` are the same arithmetic:

```
a = lo ^ (hi * 0x85EBCA77);  a ^= a>>16; a *= 0x7FEB352D; a ^= a>>15; a *= 0x846CA68B; a ^= a>>16;   // hb
b = hi ^ (lo * 0xC2B2AE3D) ^ a;  b ^= b>>17; b *= 0xED5AD4BB; b ^= b>>11; b *= 0xAC4C1B51; b ^= b>>15;  // hl
```

Six 32-bit multiplies per key, all `vpmulld` / `mul.4s`. The reason for 32-bit arithmetic is that **AVX2 has no
64×64→64 multiply** (`vpmullq` is AVX-512DQ) and NEON has none either; a 64-bit mixer such as murmur's `fmix64`
would cost four `vpmuludq` + shifts + adds per multiply. `hb` selects the block/bucket, `hl` seeds the per-lane
bit positions (Bloom) or the fingerprint (cuckoo). The property tests check `hash8 == hash1` on every lane for
every backend, which is what lets a filter be built with the per-key API and queried with the batched one.

Block selection is Lemire's fast range, `(hb * nblocks) >> 32`, so filter sizes need not be powers of two. AVX2
has no 32×32→high multiply, so `mulhi_32` is emulated with two `vpmuludq` (even/odd lanes) and a blend; NEON uses
`umull`/`umull2` + `uzp2`.

### 1.2 Blocked Bloom filter (`BlockedBloom<Ops, BlockBytes, BitsPerLane>`)

A key maps to exactly one 32- or 64-byte block (one cache line or half of one). The block is 8 lanes — `u32`
lanes for 32-byte blocks, `u64` lanes for 64-byte blocks — and the key sets one bit per lane (`k = 8`) or two
(`k = 16`). Lane *i*'s position is a multiply-shift of the same `hl`:

```
pos  = (set1(hl) * salts) >> 27        // 32-byte blocks: 5 bits per lane   (>> 26 for 64-bit lanes)
mask = sllv(set1(1), pos)              // one variable shift builds all k bits
insert: block |= mask                  // one load, one OR, one store
query : testc(block, mask)             // (block & mask) == mask, one vptest -> flag
```

No loop over k anywhere. On NEON the test is `bic` (mask &~ block) on both halves, `orr`, `umaxv == 0`. On
AVX-512 the 64-byte block is one zmm, the mask is built with one `vpsllvq`, and the test is
`vptestmq(andnot(block, mask), mask) == 0` (a k-mask, no flag dance). The 32-byte variant is the split-block
design used by Impala/Parquet; the 64-byte variant trades one more `cvtepu32→epi64` + a second ymm per op (on
AVX2) for a lower FPR at the same bits/key (§3).

**Batched API.** `insert_batch` / `contains_batch` / `count_batch` share a driver that processes the input in
windows of `W` keys (default 32) with a one-window software pipeline:

1. stage 1 on window *w+1*: `hash8_keys` (8 keys per vector op), `mulhi` for block index, store `blk[]`,
   `hl[]`, issue one `prefetch` per block (`prefetchw` for inserts);
2. stage 2 on window *w*: build mask, load block, test/OR — on lines that were prefetched one window ago.

Tails shorter than 8 keys use `hash1`. The window is a runtime knob (`set_window`, ≤256) because the right
value depends on where the filter lives (§4.3).

### 1.3 Cuckoo filter (`CuckooFilter<Ops, u8|u16>`)

Standard partial-key cuckoo hashing with 4-slot buckets, `i1 = hb & (nbuckets-1)`, fingerprint
`fp = hl >> (32-F)` (0 remapped to 1, 0 = empty), `i2 = i1 ^ (fp * 0x5bd1e995 & mask)`. Buckets are 8 bytes
(`u16`) or 4 bytes (`u8`), so **both candidate buckets fit in one 128-bit register**:

```
pair = unpacklo_epi64(loadl(b[i1]), loadl(b[i2]))     // 8 x u16
hits = movemask(packs(cmpeq_epi16(pair, set1(fp))))   // bit i = slot i matches; bits 0-3 bucket i1, 4-7 bucket i2
```

Insert uses the same scan with needle 0 to find a free slot (ctz picks it), then the usual kick loop (≤500,
random slot, `i ^= alt(fp)`). `erase` clears the first matching slot; if an insert ever exhausts the kick
limit the evicted fingerprint goes into a one-entry victim stash that `contains`/`erase` check, so the
no-false-negative guarantee survives a full table. The batched lookup hashes 8 keys per vector op, derives
`i1`, `i2`, `fp` vectorially (including the `fp==0→1` fix-up with an add/shift/or, since the layer has no
compare), prefetches **both** buckets a window ahead, and then does one 128-bit scan per key.

### 1.4 The SIMD layer (`include/vf/simd.h`)

Four backends expose the same ~25 static functions over `v32` (8×u32), `b512` (8×u64 = one Bloom block) and
`v128` (one cuckoo bucket pair): `Portable` (plain loops, with pragmas asking the compiler not to vectorise),
`Avx2`, `Avx512` (inherits `Avx2`; only `b512` and a two-block test differ) and `Neon` (a logical 256-bit vector
is a pair of q-registers). The portable backend is the executable spec: the property tests require every ISA
backend to produce the identical bit array and identical answers. Writing the layer by hand instead of using
Highway kept it to ~250 lines and made the per-ISA costs visible; the price is that each new operation (e.g.
the `mulhi` emulation) has to be written three or four times. A Highway port would be mechanical — every
function here has a direct Highway equivalent (`MulHigh`, `Shl`, `AllTrue`, `BitsFromMask`).

### 1.5 Baselines and measurement

* `ClassicBloom`: k=7 double-hashed positions over the whole bit array, early-exit loop, one random cache
  line per probe. This is the "simple scalar baseline".
* `bench_portable`: the *same* blocked/cuckoo algorithms through the scalar backend, compiled with
  `-fno-tree-vectorize -fno-tree-slp-vectorize`, so the SIMD gain of the algorithm is separable from the
  algorithmic gain over the classic filter.
* Per-measurement counters via `perf_event_open` (cycles, instructions, branch-misses, L1D and LLC load misses),
  best-of-3 for lookups, chunked and summed for inserts; per-key and batched inserts alternate 1M-key chunks so
  both see the same load-factor progression (this mattered for the cuckoo filter, §5.2).
* Inputs: inserted keys uniform / sequential / clustered (runs of 64 consecutive ids); query streams 50/50
  present+absent, all-absent, and Zipf(1)-skewed present keys. Filters are filled to their design point
  (10 bits/key for Bloom, 95 % load for cuckoo), so a 1 GiB Bloom filter holds 859 M keys — keys are generated
  from a seeded stream instead of being stored.
* Allocations ≥ 4 MiB are 2 MiB-aligned mappings with `MADV_HUGEPAGE`; `--no-hugepages` turns it off (§4.4).

Reading this together with §2:

* **Blocked costs ~1–1.5 bits/key over a classic Bloom filter at the same FPR** (1 % FPR: classic ≈ 9.6 bpk,
  blocked32 ≈ 10.7 bpk; 0.1 %: ≈ 14 vs ≈ 15.5) — the usual price of confining k bits to one line. The

  per op on AVX2 (§5.4).
* **k = 16 in a 64-byte block is only useful above ~18 bits/key.** Below that it over-saturates the block

  512-bit block at 10 bpk is 8, which is what `blocked64` does.
* **cuckoo16 is the structure for low FPR**: at 17 bpk it is 9× better than blocked32 and 2.6× better than the

  improves with more memory (it is ≈ 2·4·load / 2¹⁶; extra memory only lowers the load factor). cuckoo8 has
  a floor of ~3 % × load: cheap, deletable, but never below 0.8 % even at 32 bpk.
* For the common "~1 % FPR, 8–12 bits/key, no deletes" regime, `blocked32` and `blocked64` are the right
  choice: at 10–12 bpk they are 3–4× faster per lookup than the cuckoo filters while holding 1.7× more keys
  per byte than cuckoo16 could.

## 4. The memory-bound regime, explicitly

### 4.1 What the machine can do: random 64-byte accesses (`membench`, ns per line, THP on)

| working set | 1 access in flight (latency) | 4 | 8 | 16 | 32 in flight |
|---|---|---|---|---|---|
| 1 MiB | 8.6 | 2.04 | 1.03 | 0.59 | 0.52 |
| 4 MiB | 58.0 | 10.8 | 6.57 | 2.69 | 1.58 |
| 16 MiB | 74.1 | 17.1 | 6.27 | 2.47 | 1.97 |
| 64 MiB | 112 | 30.1 | 13.3 | 6.16 | 3.64 |
| 1 GiB | 118 | 31.3 | 16.0 | **8.35** | 6.13 |

This guest's cache hierarchy is not what `lscpu` reports: anything beyond the 2 MiB L2 costs 60–120 ns
of latency (the 260 MiB L3 is shared with the whole socket and sits across a mesh/virtualisation boundary).
So "fits in L2" vs "exceeds LLC" here is 1 MiB vs 1 GiB, with 16 MiB an intermediate point that is already
latency-bound but still has some L3 locality. A single core sustains at most ~16–32 outstanding line fills
(the L1D fill buffers), which caps random access at **~6–8 ns/line ≈ 120–160 M lines/s** regardless of DRAM
bandwidth (that is only 8–10 GB/s of 64-byte lines; the bus is not the limit, the number of outstanding
misses is).

### 4.2 Where the filters sit against that ceiling (1 GiB, AVX2)

| | lines touched per lookup | measured ns/lookup | ns per line | % of the 16-in-flight ceiling (8.35 ns/line) |
|---|---|---|---|---|
| classic-k7 per-key | ~2 on absent keys (early exit), 7 on present | 85.8 | ~19 | — (latency-bound, data-dependent branch stalls the chase, §5.1) |
| blocked32 per-key | 1 | 31.6 | 31.6 | 26 % — MLP comes only from the reorder buffer (~4 lookups in flight) |
| blocked32 batch W=32 | 1 | 11.3 | 11.3 | 74 % |
| blocked32 batch W=128 | 1 | 8.3 | 8.3 | **100 %** |
| cuckoo16 per-key | 2 | 48.0 | 24.0 | 35 % |
| cuckoo16 batch W=128 | 2 | 13.7 | 6.9 | ~90 % of the 32-in-flight ceiling (6.13 ns/line; the two lines of one key overlap) |

So: at 1 GiB the batched Bloom lookup is exactly at the random-access roofline of the core, the per-key API is
a quarter of it, and the classic filter is a factor 10 below. The SIMD mask/test work is invisible at this size
— the portable backend's batched lookup at 1 GiB is 22.6 ns (2× AVX2), not 4×, because half of its cost is the
same memory wait. The vector work only shows fully in L2, where the blocked32 batch lookup is 3.0 ns ≈ 6
cycles at 2.1 GHz for hash + mask + test + store.

| structure | size | W=1 | 4 | 8 | 16 | 32 | 64 | 128 | 256 |

| blocked32 | 1 GiB | 39.49 | 18.46 | 12.98 | 10.62 | 10.73 | 10.60 | 8.27 | 8.37 |
| cuckoo16 | 1 MiB | 11.30 | 6.97 | 5.03 | 5.08 | 4.46 | 4.36 | 4.84 | 5.34 |
| cuckoo16 | 16 MiB | 17.24 | 10.30 | 12.35 | 13.28 | 11.14 | 11.25 | 9.70 | 9.15 |
| cuckoo16 | 1 GiB | 58.63 | 24.26 | 19.54 | 19.09 | 16.13 | 15.99 | 13.73 | 14.31 |

W=1 is the batched code path with no lookahead (the prefetch is issued immediately before the load) and is
*slower* than the per-key API — the pipeline's bookkeeping (storing and reloading `blk[]`/`hl[]`) costs
~4 ns per key with nothing to hide it behind. In L2 the knee is at W=8–16 and W=256 hurts (the two 2 KiB
index buffers plus the output start competing for L1). Out of cache the optimum keeps moving right:
W=128 is needed to fill 16+ line-fill buffers because stage 2 of window *w* has to be long enough to cover
the latency of the prefetches issued for *w+1*. The default of 32 is a compromise; a production build that
knows its filter is DRAM-resident should use 128.

### 4.4 Huge pages: what a random lookup pays for the page walk (1 GiB, ns/op)

| structure | API | op | 2 MiB pages (THP) | 4 KiB pages | ratio |
|---|---|---|---|---|---|
| classic-k7 | per-key | lookup | 85.8 | 115.6 | 1.35× |
| blocked32 | per-key | lookup | 31.6 | 32.1 | 1.02× |
| blocked32 | batch | lookup | 11.3 | 17.5 | **1.55×** |
| blocked32 | batch | insert | 7.3 | 15.5 | 2.13× |
| cuckoo16 | per-key | lookup | 48.0 | 53.4 | 1.11× |
| cuckoo16 | batch | lookup | 16.3 | 33.8 | **2.07×** |

With 4 KiB pages a 1 GiB filter needs 262 144 PTEs (2 MiB of page tables, which do stay in L2/L3), and
every lookup is also an L2-TLB miss (2048 entries × 4 KiB = 8 MiB reach). The per-key paths barely notice:
the page walk overlaps with the latency they were already paying. The batched paths lose 35–50 % because a
software prefetch that misses the TLB has to complete the walk before the line fill can even start, so the
effective lookahead per window halves. Memory-bound filters should be in huge pages; `vf::alloc_zeroed_aligned`
does `MADV_HUGEPAGE` on anything ≥ 4 MiB for this reason.

## 5. What vectorised well, what didn't, and why

### 5.1 The classic baseline is branch-bound before it is memory-bound

In L2 the classic filter costs 22–28 ns (≈ 50–60 cycles) for what is 2–7 loads plus a bit test each. The
reason is the early-exit loop: at the design point half of all bits are set, so for an absent key each probe
is a coin flip and the `if (!bit) return false` mispredicts almost every lookup (an absent-key lookup has
on average ~2 probes and ends on a taken-miss that was predicted ~50/50). The all-present Zipf stream in §2.4
makes the branch always-taken and the same code runs in 12.9 ns. Out of cache the branch is worse than a
mispredict: the next probe address is only computed after the branch resolves, so the 7 random lines of one
key are fetched serially and the OoO engine cannot run ahead into the next key either. The blocked filters
have no data-dependent branch anywhere on the lookup path — `vptest` → `setc` — which is why their cost is
flat across absent/mixed/present in §2.4.

### 5.2 Cuckoo lookup: one `||` cost 2.3×

The first version of `CuckooFilter::contains` was `scan_pair(...) != 0 || victim_hit(...)`. The short-circuit
`||` compiles to a branch on the match mask, which on a 50/50 stream mispredicts half the time:

| 1 MiB, AVX2, per-key lookup | mixed queries | all-absent queries |
|---|---|---|
| `\|\|` (branch on match) | 18.0 ns | 7.9 ns |
| `\|` (bitwise, branch-free) | 7.2 ns | 7.3 ns |

The batched path was already branch-free and unaffected (4.3 ns both ways). This is the single largest
"optimisation" in the project and it is not a SIMD one; `-DVF_CUCKOO_BRANCHY` rebuilds the slow variant.
The same lesson applies to the victim-stash check, which is written as `valid & (fp == ...) & (...)`.

### 5.3 Cuckoo insert does not batch

Batched inserts help the Bloom filters a lot (1 GiB: 27.5 → 7.3 ns, the OR into a prefetched line is
fire-and-forget). For the cuckoo filter batching gains 0–20 % (16 MiB: 60 → 53 ns; 1 GiB: 168 → 133 ns)
and at 95 % load the insert is dominated by the kick chain: each eviction computes the alternate bucket
*from the evicted fingerprint*, which is a dependent random access that no prefetch issued at window time
can cover. Average kick length rises steeply above ~90 % load, which is why the 1 GiB insert costs 130–170 ns
(≈ 1.2 dependent DRAM accesses per key) while the lookup costs 16 ns. The SIMD scan itself (one `pcmpeqw`
+ `pmovmskb`, needle 0 for free slots, `ctz` to pick one) is not the problem; the data dependence is.
Options that would help are algorithmic, not vector: lower load factors (cuckoo8 at 80 % load inserts 2–3×
faster), bucketized insertion with a victim queue processed in bulk, or the "sorted buckets" / semi-sorting
of the original paper (which trades the SIMD scan for 1 bit/key).

### 5.4 64-byte blocks on AVX2 are two vectors, and it shows

With 32-byte blocks the whole operation is one ymm: broadcast, `vpmulld`, `vpsrld`, `vpsllvd`, `vptest`.
With 64-byte blocks on AVX2 the 8 positions have to be widened (`vpmovzxdq` ×2), shifted as two `vpsllvq`,
and tested as two `vptest`s — about 2× the vector µops for ~20 % lower FPR. Measured in L2: 5.2 vs 6.8 ns
per-key, 3.0 vs 3.8 ns batched. Beyond L2 the difference disappears (31.6 vs 30.5; 11.3 vs 11.7). On AVX-512
the 64-byte block is one zmm and the per-key cost drops to 5.7 ns (vs 6.8 on AVX2) — see 5.6. The honest
recommendation for an AVX2-only target is 32-byte blocks unless the extra 0.3 bits/key matters.

### 5.5 The per-key API out of cache is codegen-fragile; the batched API is not

The per-key lookup loop beyond L2 is bound by how many iterations the reorder buffer can hold, since that is
where its memory-level parallelism comes from. Two builds of *identical* source (`-mavx2` vs `-mavx512*`) of
`cuckoo16` per-key lookup at 16 MiB measured 12.4 vs 23.5 ns, reproducibly; the diff of the two loops is
nothing but register allocation and two loop-invariant reloads (`mask_`, `victim_.i`) that one compiler
placed after the `out[i]` store. In a separate harness the ordering flipped (AVX2 16.8 ns, AVX-512 13.0 ns), and
simply not writing `out[]` gave 12.5 ns for both. Without hardware counters the mechanism cannot be pinned
(candidates: memory-disambiguation stalls on the reload after the byte store, or a loop-alignment effect on
the µop cache); the point for the design is that **per-key throughput beyond L2 varies ±2× with incidental
codegen, while the batched path, whose MLP comes from explicit prefetches, is within 3 % across backends**
(blocked32 batch at 1 GiB: 11.26 / 11.59; cuckoo16: 16.34 / 16.22).

### 5.6 AVX-512: what changes, what was measured, what wasn't

Implemented and measured (`Avx512` backend, inherits `Avx2`):

* **64-byte block as one zmm**: `vpsllvq zmm` builds the 8×u64 mask from the 8 positions in one instruction,
  `vptestmq` on `andnot(block, mask)` returns the "missing bits" k-mask, `kortest` gives the flag. Per-key
  lookup 6.81 → 5.67 ns (1 MiB), 8.57 → 6.13 ns for k=16. Batched: no change (3.83 vs 4.18, memory and
  bookkeeping dominate).
* **Two 32-byte blocks per zmm** (`Avx512::test2_blocks32`, `-DVF_AVX512_PAIRED_LOOKUP`): the two keys' blocks
  are gathered into one zmm with `vinserti64x4`, the two masks likewise, one `vptestmd` yields a 16-bit
  mask and both answers. It is **35 % slower** than one key per ymm (3.70 vs 2.67 ns in L2) and is off by
  default. Per pair it saves one `vptest`+`setc` but adds two `vinserti64x4` (port-5 shuffles) and the
  `kmov`/split/`sete`×2 extraction, so it is more µops per key, with more of them on port 5; the compare
  was never the bottleneck. This is the general lesson of this project: the natural vector in a blocked
  filter is *one key's block*, and widening across keys only pays when the cross-key work is itself
  wide (hashing is; the block test is not).

Not implemented, would change the design:

* **64-bit hashing.** `vpmullq` makes a proper 64-bit mixer 8-wide; the current 32-bit split exists only
  because AVX2/NEON lack it. With it, a single 64-bit hash could feed block index (high bits) and lane
  positions (low bits) without the two-output construction, and the scalar/vector agreement would hold for a
  standard mixer such as `fmix64`.
* **16-wide stage 1.** `hash8` becomes `hash16` on zmm (`vpmulld zmm`), halving the per-window hashing
  instructions. Stage 1 is ~25 % of the in-L2 batched cost, so this is worth maybe 10 %; out of cache it is
  nothing.
* **Output compaction.** `vpmovm2b`/`kmov` would write 16 results of a window as one 16-byte store instead of
  16 byte stores.
* **Cuckoo**: `vpcmpeqw` with a k-mask and `kmov` replaces `pcmpeqw` + `packs` + `pmovmskb` (one fewer shuffle),
  and `vpermt2w`/`vpcompressw` would make the 16-bit bucket pair of 4 keys scannable in one zmm; neither
  touches the real cost, which is the two line loads.
* **Gathers do not help.** `vpgatherdd` of 16 keys' first words would still miss 16 lines and then need the
  full blocks anyway; a gather is implemented as 16 loads on every current core.
* **Frequency.** On client and older server parts heavy 512-bit use lowers the clock; on this guest it could
  not be measured.

### 5.7 NEON

The NEON backend was validated under qemu (all property tests, bit-identical FPR to x86) but not timed.
Codegen of the per-key 32-byte lookup is what the design predicts: 9 `mul` (6 scalar hash + 2 vector salt
multiplies + 1 fast-range), 2 `ushr`, 2 `ushl` (variable shift is `vshlq_u32` with a signed shift vector —
no `sllv` needed), 2 `bic`, 1 `orr`, 1 `umaxv`, 1 `cset`. Two things cost more than on x86: the logical
256-bit vector is two q-registers (every op is emitted twice, which is fine for throughput on cores with 4
NEON pipes but doubles the instruction count), and there is no `movemask`; the cuckoo scan narrows the
compare result and does a per-lane bit-table AND + `addv` (4 instructions where x86 needs 2). `umaxv` is a
cross-lane reduction (3–4 cycles latency on most cores) on the critical path of every per-key test; the
batched path hides it. SVE would remove both the double-emission and the reduction (predicate registers).

### 5.8 Things that did not need vectorising

The whole batched pipeline is "vectorised" only in stage 1 (8 keys per hash) and within a key in stage 2.
There is no useful cross-key vectorisation of stage 2 for any block size that fits a register, because
each key's data is a different random line — this is a memory-level-parallelism problem, and prefetch
distance (W) is the knob that matters (§4.3), not vector width. The best in-L2 batched number, 3.0 ns ≈ 6
cycles per lookup, is already ~1.5 ns of hashing, ~1 ns of mask/test, and ~0.5 ns of buffer bookkeeping;
the remaining factor of two to the AVX-512 "ideal" would come from fusing stage 1's stores and stage 2's
reloads (keeping `blk`/`hl` in registers for a window of 8), not from wider vectors.

## 6. Correctness

* `tests/test_props.cpp` (`ctest`): for every compiled-in backend × {blocked32, blocked64, blocked32×2,
  blocked64×2, cuckoo16, cuckoo8} × {uniform, sequential, clustered} × filter sizes from 32 B to 64 KiB,
  random op sequences are mirrored into the portable backend and a `std::unordered_set` /
  `unordered_map` model: hash lanes agree with `hash1`, bit arrays agree byte-for-byte after per-key and
  after batched inserts, `contains_batch` agrees with `contains` and with the portable batch for sizes
  0/1/7/8/9/31/33/257/1001 with random windows, no false negatives, cuckoo erase of a present key always
  succeeds and never loses a duplicate, cuckoo batch and per-key inserts produce the same table and the
  same failure count; FPR sanity bands at 10 bpk. 2.2 M checks in the AVX2 binary (portable + AVX2
  backends), 3.3 M in the AVX-512 one; the AArch64 binary runs the same suite under qemu (`neon` vs
  `portable`).
* `tests/fuzz_ops.cpp`: libFuzzer harness over a tiny key space (dense fingerprint and block collisions),
  every backend vs portable vs model, including erase and the victim stash; 400 k runs with ASan+UBSan on
  AVX2 and 118 k on AVX-512 found nothing after the branch fix. A sanitizer-free random driver of the same
  harness runs in `ctest`.
* One bug was found by the tests rather than by thinking: the first FPR sanity test sized the cuckoo tables by
  bytes and the power-of-two bucket rounding silently halved the capacity, so the 95 % load target became 100 %
  and inserts failed; the fix was to size by capacity.

## 7. Reproducing

```
cmake -S . -B build && cmake --build build -j && ctest --test-dir build
scripts/run_all.sh build results && python3 scripts/make_report.py results
```

The matrix takes ~50 min, dominated by filling the 1 GiB filters to their design point (859 M Bloom
inserts, 510 M cuckoo16 inserts at 95 % load). On a machine with a PMU the CSV gains cycles, IPC, L1D/LLC
misses and branch misses per operation (`cycles_src=hw`); `scripts/perf_stat.sh` cross-checks with
`perf stat`.
